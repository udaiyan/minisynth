# AI-Assisted Test Generation Policy

How AI tooling is used to generate tests in this repository, what it's
allowed to do, and what a human reviewer must check before anything
generated by it is merged.

This is a working policy, not a manifesto. It exists because AI
assistance is now a normal part of a developer's toolkit, and treating
it as either forbidden or unremarkable both lead to bad outcomes.

---

## 1. Scope

This policy covers any test code — unit, integration, or component —
that was substantially generated by a large language model or a
code-completion tool.

It does not cover:

- AI-assisted **refactoring** of existing hand-written tests
- AI-assisted **documentation**
- AI-generated **production** code (the production code in this repo is
  hand-written; if that changes, this policy needs a companion)
- Test **ideas** or **edge cases** suggested by AI but implemented by
  hand

The line is whether AI produced the test code that gets committed. If
yes, this policy applies.

---

## 2. Tooling selection

### What's in scope

| Tool | Use | Notes |
|---|---|---|
| GitHub Copilot | In-editor completion | Best for boilerplate: fixtures, `SECTION` scaffolding, repetitive assertions |
| Claude / ChatGPT | Conversational generation | Best for "write me tests for this class" — requires more review |
| Copilot Chat | In-editor conversation | Middle ground; has file context |

### What's out of scope

- **Autonomous agents** that open pull requests unattended. Every commit
  needs a human author who can defend it.
- **AI test-generation services** that run against a live codebase and
  file results directly. The review overhead exceeds the benefit at this
  project's size.
- **Any tool that uploads source code to a third party without an
  explicit data-handling agreement.** For a public repo this is moot, but
  the rule stands for anything closed-source.

### Why these criteria

We selected for tools that **augment a developer's judgement** rather
than replace it. The tool proposes; the developer decides. Anything that
inverts that relationship — where the developer is reviewing the tool's
output rather than the tool assisting the developer's output — is out
of scope.

---

## 3. What AI is good at

Being specific about this matters. Vague praise produces vague usage.

**Boilerplate.** Given an existing test file with a clear pattern,
generating a new test that follows it is nearly mechanical. Use AI here
without hesitation.

**Enumerating edge cases.** Ask "what inputs would break this function?"
and you get a useful list. The list needs filtering, but it's faster
than thinking of them yourself.

**Naming.** Given a function and a behaviour, generating a descriptive
test name is fast and low-risk.

**Coverage gap analysis.** Given a source file and its test file, "what
branches aren't covered?" is a question AI answers well.

**Translating intent to syntax.** "I want to assert that the filter
output is finite for 10,000 samples" becomes runnable code quickly.

---

## 4. What AI is not good at

This section is longer, and deliberately so. It's the one that
determines whether a generated test is safe to merge.

### Floating-point tolerance

AI defaults to `WithinAbs(x, 0.001f)` regardless of context. A tolerance
that's fine for a filter output is too tight for a value that's
accumulated across 8,820 samples. It doesn't know the difference unless
told.

**Caught in this repo:** the envelope release test asserted the level
reached exactly zero after the nominal release time. It fails because
`0.5 / 8820` isn't representable in binary. No human would have written
that test, because a human knows floating-point arithmetic is lossy.

### Off-by-one in loops

Counting samples is where AI-generated tests consistently fail.
`for (int i = 0; i < 25; ++i)` versus `24` is a distinction that
requires holding the phase-advance convention in your head.

**Caught in this repo:** three separate test failures in
`test_oscillator.cpp`, all caused by incorrect loop counts.

**Mitigation:** push counting into named helpers (`sampleAt(osc, 26)`)
so the numbers in the test encode meaning rather than mechanism.

### Discrete vs continuous

AI reasons about mathematical ideals. A saw wave goes from −1 to +1. A
*sampled* saw goes from −1 to `1 − 2/N`. The distinction matters when
you write the assertion.

**Caught in this repo:** a test asserted the saw reached `+1.0`. It
never does — the sampled maximum for a 100-sample cycle is `0.98`.

### Missing the "why"

AI-generated tests tend to assert on implementation. "The level is 0.5
after 50 samples" is a statement about the current implementation. "The
release takes the configured time regardless of starting level" is a
statement about the contract.

**Contract assertions survive refactoring. Implementation assertions
don't.** A reviewer's job is to spot which one they're looking at.

### `REQUIRE` everywhere

AI defaults to `REQUIRE` for everything. Inside a 1000-iteration loop
this produces 1000 identical failure messages instead of one useful
summary. Knowing when to use `CHECK` is a judgement call.

### Compiler-specific behaviour

Anything involving `-Wswitch`, missing `default:` cases, `-Wfloat-equal`,
or platform-specific quirks is likely to be wrong. AI writes portable
C++; we deliberately use non-portable patterns (switches without
`default:`) to let the compiler catch mistakes.

### Test discovery and infrastructure

AI won't know that a `ScopedJuceInitialiser_GUI` at namespace scope
hangs Catch2's `--list-tests` pass. It won't know about our
`catch_discover_tests` setup. It won't know that the CMake must list
source files before they exist, or that `juce_add_console_app` needs a
specific main.

**Infrastructure failures are silent.** A generated test that compiles
but never runs is worse than no test. Always verify a new test appears
in `--list-tests`.

## 5. Prompting standards

Prompts should be specific enough that the output is reviewable. These
are the minimum requirements.

### Provide the file, not a description

    ✗  "Write tests for an oscillator class"
    ✓  [attach Oscillator.h and Oscillator.cpp]
       "Write tests for the oscillator in the attached files. Follow
        the conventions in the attached test_oscillator.cpp."

Conventions are not guessable. Every project has them, and AI will
invent a different one unless shown an example.

### State the constraint, not the goal

    ✗  "Test the envelope's release"
    ✓  "Test that the release takes the configured time regardless of
        the level at note-off. Use a tolerance of ±100 samples."

The constraint is where the bug lives. Stating it forces you to think
about it before the AI does.

### Name the anti-patterns

If you know a class of bug you're worried about, say so:

> "Do not assert exact equality on any value that has been accumulated
> across multiple samples."

This is more effective than reviewing the output and catching it.

### One test at a time

Generating a whole suite produces a wall of code that's hard to review.
Generating one test produces something you can hold in your head.

**Rule:** no more than three related tests per generation. Anything
larger gets split.

### Require the reasoning

Ask for a one-line comment per assertion explaining *why* it's checking
that. It surfaces mistakes early — if the AI can't explain it, the
assertion is probably wrong.

## 6. Review discipline

**Every AI-generated test is reviewed as if it were written by a
developer in their first month.** The bar is not lower because a machine
wrote it. If anything, it's higher, because the failure modes are less
familiar.

### The checklist

A reviewer must verify all of the following before approving.

**Correctness**
- [ ] The test fails when the code is deliberately broken. Verify this.
      A test that passes against broken code is worse than nothing.
- [ ] The assertion is on the *contract*, not the implementation.
- [ ] The tolerance is appropriate to what's being measured.
- [ ] Any floating-point comparison is defensible.

**Conventions**
- [ ] Name follows `<Class>: <behaviour>`.
- [ ] Carries the correct tag.
- [ ] Uses `CHECK` vs `REQUIRE` appropriately.
- [ ] Reuses existing helpers rather than reimplementing setup.
- [ ] No `default:` case on a switch over a project enum.

**Robustness**
- [ ] Runs deterministically. Run it 10 times; it should pass 10 times.
- [ ] Doesn't depend on execution order.
- [ ] Doesn't depend on wall-clock time or system state.
- [ ] If it uses loops, the loop bounds are correct.

**Integration**
- [ ] Appears in `--list-tests`.
- [ ] Appears in Test Explorer / CTest after a reconfigure.
- [ ] Passes in CI on both Windows and Linux.

### The critical one

**Break the code and check the test fails.**

A test that passes against a deliberately broken implementation is a
false confidence. It's the single most common failure mode of
AI-generated tests, because the AI has learned to write assertions that
match the code as written — including its bugs.

For every generated test:

1. Change the production code to break the behaviour.
2. Run the test.
3. Confirm it fails.
4. Revert the change.

If it still passes, the test isn't testing anything. Rewrite it or
delete it.

## 7. Quality thresholds

A generated test must meet all of the following before it's merged.

| Threshold | Requirement |
|---|---|
| Fails against broken code | Mandatory — see §6 |
| Deterministic | 10/10 passes on the local machine before commit |
| CI-green on both platforms | Windows and Linux |
| No new warnings | Build must not add `-W` output |
| Coverage-positive | The commit must not reduce coverage |
| Reviewable | Reviewer can explain every assertion without asking |

The last one is the softest and the most important. **If a reviewer
can't explain an assertion, the test shouldn't merge — regardless of
whether it passes.**

### What this means in practice

A typical AI-generated test file of 20 tests will have:

- Around 12 that are correct or nearly so
- Around 5 that need tolerance adjustments or naming fixes
- Around 3 that should be deleted

That's a reasonable ratio. It's still faster than writing 20 tests by
hand. But it only works if the review actually happens.

## 8. When an AI-generated test fails

A failed generated test is information. The first question is always:

**Is the test wrong, or is the code wrong?**

Do not assume the test is wrong. AI-generated tests that fail are
sometimes catching real bugs.

### Triage

1. **Does the test's premise make sense?** Read the test name out loud.
   Does the behaviour it describes actually belong to this class? If
   not, the test is testing the wrong thing.

2. **Is the assertion on a discrete or continuous value?** See §4. If
   it's asserting on the mathematical ideal of a discrete system, the
   test is wrong.

3. **Is the tolerance too tight?** For any accumulated value, yes.
   Widen it or restructure.

4. **Does the code actually do what the test expects?** If the test is
   reasonable and the code disagrees, the code is probably wrong.

5. **Is it an infrastructure issue?** Test not discovered, wrong tag,
   missing from CMake, wrong fixture. These are silent failures and
   need to be ruled out explicitly.

### If you can't decide

Delete the test and write it by hand. If you can't articulate what
behaviour it's checking well enough to debug it, you can't review it
either, and it shouldn't be in the suite.

## 9. Disclosure

Commits containing AI-generated test code should say so.

    Add envelope release tests (AI-assisted)

That's the entire requirement. No author attribution, no link to the
prompt, no tool name. Just a marker so that when a pattern of failures
emerges later, there's a trail to follow.

**Why bother.** If a class of generated tests turns out to be
systematically wrong — say, all the filter tolerance tests — the commit
message is how you find them. Without it, you'd have to read every test
in the repo.

**What not to do.** Don't add generated-code headers, don't add
co-author lines, don't add commit trailers. This isn't a legal
disclosure; it's a bookkeeping marker.

---

## 10. What this policy doesn't cover

**Whether to use AI at all.** That's a team decision, not a policy
decision. This document assumes the answer is yes and governs *how*.

**Tooling procurement.** Which licence, which tier, what it costs — not
a technical question.

**Generated code in production.** Different risk profile. Different
policy. Not written yet.

**AI in code review.** A tool suggesting "this test looks weak" is
useful; a tool approving or blocking a merge is not. The policy would
be different and is out of scope here.

---

## 11. Review of this policy

This document reflects practice as of the repository's current state.
It should be revisited when:

- A generated test causes a production bug
- The review overhead exceeds the time saved
- A new tool enters the toolkit
- CI catches a flaky generated test

**The last one is the important one.** Flakiness in generated tests
means the review isn't catching something, and the checklist in §6 needs
tightening.
